# Decision: MCP server `flagpole-mcp` (project scope, `.mcp.json`)

- **Problem / trigger**: the `ui-tester` agent's scenarios begin "Given `new_banner` is enabled at 100 percent in dev". Its tool list is the browser and this server; the browser route means signing in as an operator and clicking through the web app, which is the very thing under test. Serves `004-flagpole-mcp`.
- **The honest part**: a shell command with a token would do this job for a human — `curl -X PUT .../flags/new_banner/env/dev`. The server exists because the agent cannot run shell commands, and because building one MCP server is a stated goal of this project. That is a learning trigger, not a product one, and the spec's Assumptions say so in the same words.
- **Alternative rejected**: a skill wrapping `curl` (works for a human, not for the browser-driving agent, which has no Bash); `cluster-status-mcp` as a second server (cut — see `anti-patterns.md`); an HTTP transport (a port, and authentication of the assistant to the server, for a child process of the session).
- **Limits**: stdio, no port. Three tools, one resource, one prompt — the smallest surface that exercises all three capability kinds. No cache, no paging, no evaluation, no flag deletion, no audit reading. Argument rules live in the tools' published schemas, so the assistant is told them in advance and a breaking call never reaches the flag service.
- **Least privilege**: it signs its own short-lived token with its own key pair (not the consumer's, so revoking one does not revoke the other) and holds operator rights only because the flag service was configured to grant them to its issuer — the operator slot, 001 FR-020. Off by default; **never set in the production overlay**. Nothing in the service can tell a real production from a demo, so that boundary is the deployment's and feature 005 checks the manifests. In the viewer slot the same server reads and is refused writes, and says which.
- **Audit**: changes made here appear as `who = flagpole-mcp`. That is the truth — the assistant made the change — and it is why the server does not borrow a person's token, which would record someone as the author of a change they did not make.
- **Not done**: no live key rotation (a rotated key is picked up on restart, as in 003); no shared package for the forty-line token signer — what the two services share is the machine-readable token contract both suites assert against, which removes the drift risk duplication actually carries. Signal to extract a package: a third service needing it.
- **Verification** (2026-09-02, output in `docs/walkthrough.md`): 61 unit tests; the real process started over stdio against a running flag service and listed `list_flags, get_flag, set_flag_state`, `flagpole://flags`, `rollout_check`; `set_flag_state` at 100 in dev, then the consumer rendered `enabled=true reason=rollout_hit` with no restart; `GET /audit` showed `who = flagpole-mcp`; with the grant removed the same write returned `kind: forbidden`; with the flag service stopped every tool returned `kind: unreachable` naming the address.
